# Supabase: транзакції 3.1 і міграції v3

## Увімкнення захисту операцій 3.1

`migrations/0004_legacy_atomic_operations.sql` працює з чинними таблицями
`reports`, `work_days`, `work_day_assignments`. Він незалежний від 0001/0002:
для поточного оновлення не потрібно переносити дані на v3.
У версії 3.2 файл отримав номер 0004: номер 0003 вже зайнятий
`0003_client_history_view.sql` з GitHub. Це те саме оновлення захисту
платежів, раніше підготовлене як `0003_legacy_atomic_operations.sql`.

У робочій базі це оновлення ще не застосовано: у цьому середовищі є лише
відкритий ключ, без адміністративного підключення до БД.

1. Перевірити актуальну резервну копію робочої бази.
2. У Supabase Dashboard → SQL Editor виконати **лише 0004** повністю.
   Файл виконується транзакцією; при помилці зміни відкочуються.
3. Перезавантажити застосунок. Функції визначаються автоматично;
   додатковий прапорець середовища не потрібен.

Міграція додає погоджену ставку запису, точність годин, індекси,
захист власника клієнта/працівниці, транзакційне збереження, атомарну
масову оплату й ключі повторних операцій. Функції виконуються з правами
користувача та RLS, доступні лише авторизованим користувачам.

До застосування 0004 працює сумісний старий спосіб збереження зі спробою
відновлення після помилки. Він не гарантує атомарності чи захисту повтору
платежу між різними пристроями. Повні гарантії потребують SQL-оновлення.

Автоматичні перевірки: `src/data/tests/atomicSql.test.ts` піднімає чинну
стару схему в PostgreSQL/PGlite і перевіряє транзакції, відкат, повтори,
одночасні платежі, ізоляцію користувачів та збереження історії видаленої
працівниці. Це локальна перевірка; після застосування потрібна перевірка
операцій через реальний PostgREST у робочому середовищі.

## ⚠️ Стоп-крапка (дія користувача)

Агент не має доступу до продової БД (тільки anon-ключ), тому міграції
готові, але **застосовуєш їх ти** — у [Supabase Dashboard → SQL Editor](https://supabase.com/dashboard):

1. **Бекап**: Dashboard → Database → Backups → переконатися, що є свіжий.
2. Виконати `migrations/0001_v3_schema.sql` (створює нові таблиці/в'ю; старі не чіпає).
3. Виконати `migrations/0002_backfill_v3.sql`; звірити контрольні суми в
   результаті (рядки `old`/`new` для кожного user_id мають збігтися).
4. Прогнати `tests/rls_check.sql` (перевірка ізоляції).
5. Повідомити агенту/у наступній сесії: «міграції застосовано» — фронт
   перемикається на `work_days_v3` малим PR (список місць — у
   `src/data/README.md`).

Міграції 0001/0002 нижче — окремий майбутній перехід схеми.
Поточний застосунок працює через `src/data/` з чинною схемою та
сторінковими вкладеними запитами; агрегати обчислює `src/domain/stats.ts`.

## Каталоги

- `migrations/` — 0001/0002/0003 для майбутньої v3; незалежна 0004 для чинної схеми.
- `tests/` — перевірки RLS.
- `legacy/` — історичні розсипні .sql з кореня репо (застосовані колись
  вручну; збережені для контексту, не запускати).
