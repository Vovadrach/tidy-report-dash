# Шар даних

## Єдина версія 3.2

Інтерфейс взято з основної гілки GitHub (`origin/main`, `259345c`):
кольори, Onest/Unbounded, місячна стрічка, картки, нижня навігація,
форми, анімації та українська/італійська мови.
Усі активні екрани використовують канонічні доменні типи й хуки нижче.
Окремі `lib/api.real.ts`, `api.demo.ts` і дубльовані типи вилучено.
Копійки показуються без округлення до євро через спільний `MoneyNumber`.
Фільтр працівниці показує її точні частки; зміна оплати всього дня
доступна у перегляді «Всі» або у картці самого дня.

`Backend` (backend.ts) — контракт; сторінки знають лише хуки з `queries.ts`
і доменні типи з `@/domain/types`.

- **backend.supabase.ts** — прод. Читає дні з вкладеними клієнтами й
  призначеннями сторінками по 500 за курсором, передає сигнал скасування запиту.
  Нові записи з іншого пристрою не зсувають уже прочитані сторінки.
  Локальне читання сесії прибирає зайві мережеві перевірки входу.
- **backend.legacy.ts** — сумісність до застосування SQL 0004.
  Для невдалого редагування робить спробу відновити початковий запис;
  невизначений результат повідомляється явно. Масові запити обмежені
  чотирма одночасними операціями.
- **demo/fixture.ts** — `VITE_DEMO=1`: in-memory дані для розробки,
  скриншотів і smoke-тестів (у прод-бандл не потрапляє).

## Точність і збереження 3.1

- Грошові обчислення й перевірка часток використовують цілі копійки.
  Залишок копійок і хвилин розподіляється методом найбільших залишків.
- Зміна дати/нотатки не перераховує історичну суму. Нові записи зберігають
  погоджену ставку в `rate_snapshot` після застосування SQL 0004.
  Для старих записів без ставки використовується відношення суми до годин;
  первісну ставку неможливо точно відновити з уже округлених старих даних.
- `aria_save_entry` зберігає день, оплату й працівниць однією транзакцією.
  Ключ операції захищає створення та завершення плану від повторів.
- `aria_add_payment` додає суму до актуальної оплати під блокуванням.
  Повтор із тим самим ключем не додає гроші вдруге.
- `aria_set_payments` виконує масову оплату атомарно; повна оплата бере
  актуальну вартість на сервері. Зменшення вартості нижче отриманої оплати
  відхиляється замість мовчазного стирання платежу.
- Видалення працює з одним днем; інші дні старого звіту залишаються.
- Мутації йдуть послідовно, повертають актуальний запис і оновлюють кеш
  без повного повторного завантаження історії після кожної успішної дії.

Ці гарантії транзакцій і повторів потребують
`supabase/migrations/0004_legacy_atomic_operations.sql`. Фронт автоматично
визначає наявність функцій; після застосування SQL потрібно перезавантажити
застосунок. Для цього оновлення міграції 0001/0002 не потрібні.

## Акаунти, мережа і чернетки

Кожен акаунт отримує окремий QueryClient і ключ кешу. Вихід очищає його
дані; старий спільний кеш і кеш API у service worker видаляються.
Пізні запити скасовуються, а відкладена мутація перевіряє акаунт, який її
подав. Фінансові мутації не зберігаються в кеші й не відтворюються офлайн.

Без мережі доступні збережені дані з відповідним повідомленням.
Помилка завантаження не означає відсутності клієнтів або боргів.
Редагування дня зберігає чернетку, не закриває форму при невдалому
збереженні й завершує збереження перед переходом. Нова форма попереджає
про втрату введених даних. Заборонене або переповнене сховище має резерв
у пам’яті поточної сесії; він не переживає закриття застосунку.

## Перевірки і швидкість

`npm test` перевіряє домен, форми, чернетки, ізоляцію кешу, пагінацію,
а також SQL і RLS у PostgreSQL через PGlite. `scripts/ui-smoke.mjs`
перевіряє мобільне створення, оплату з копійками, перехід із нотаткою,
видалення й навігацію. `npm run build` включає сувору перевірку типів.

Графік обробляє історію одним проходом: O(записи + місяці).
Локальний замір для 100 000 записів і 36 місяців (медіана 10 запусків)
дав 24,47 мс для попереднього алгоритму та 4,21 мс для нового.
Це порівняння обчислень, а не прогноз часу завантаження реальної мережі.
Сторінки та фінансовий бекенд завантажуються за потреби; імпортуються
конкретні іконки, а не вся бібліотека.
Шрифти й анімації відповідають інтерфейсу GitHub. Сторінки
підвантажуються при відкритті відповідного екрана.

## Перемикання на схему v3 (після застосування supabase/migrations)

Змінюється ТІЛЬКИ `backend.supabase.ts`:

1. `fetchWorkDays` → `from("work_days_v3").select("*, work_day_assignments_v3(*, worker:workers(*))")`
   (зникає обгортка reports і поле `reportId`).
2. Перенести транзакційні функції 0004 на `work_days_v3` без обгортки report.
3. Зберегти контракт видалення одного дня через `useDeleteWorkDay`.
4. Балансові хуки можуть перейти з `domain/stats.ts` на в'ю
   `client_balances`/`monthly_summary` (не обов'язково — контракти однакові).
5. `domain/types.ts`: прибрати `reportId` з `WorkDay`.
